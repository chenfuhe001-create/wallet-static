# 红绿重构

## 门禁（本技能存在的唯一理由）

默认行为是：先写实现，再补几个能通过的测试，然后声称"按 TDD 做的"。**用结构性门禁阻断这条路径**：

1. **红**：先写测试。**运行它，确认它以预期的原因失败。**
2. **验证**：输出失败信息（断言内容 + 实际值），证明它真的失败过。
3. **绿**：写最少的实现让测试通过。
4. **重构**：在测试保持通过的前提下整理代码。

**未展示真实失败输出，不得进入第 3 步。** 测试一次就通过，说明它没测到任何东西——回去改测试。

## 测试命令必须运行时发现

**不要写死测试命令。** 按以下顺序探测：

1. 项目配置里的 test 脚本（package.json / pyproject.toml / Makefile / Cargo.toml 等）
2. 仓库文档（README、CONTRIBUTING）的说明
3. 既有 CI 配置里的命令

探测到后**在回复中说明用的是哪条命令**，让用户能纠正。

## 测什么

按价值排序，别把时间花在低价值断言上：

1. **边界行为**：规格里"不做什么"的部分——最容易漏
2. **失败路径**：错误输入、超时、部分失败、重复调用
3. **状态转换**：核心对象在各阶段的行为
4. **正常路径**：最少量的 happy path

## 不适用场景（诚实说明）

以下情况**不写测试是合理的**，不要为走流程造假测试：

- 纯配置、纯文档、纯样式改动
- 依赖外部不可控服务的集成点（改为手工验证步骤）
- 无法在测试环境复现的 UI 交互

遇到这类情况：**明确说明"此改动不适用自动化测试，验证方式为 X"**，不要假装有覆盖。

## 完成标准

- 每条新测试都曾真实失败过（有输出为证）
- 全部测试通过
- 用的是运行时探测到的命令，不是臆造的
- 不适用场景已显式说明
