# 如何写出有效的技能

技能是**概率性**指令：它引导行为，但不保证执行。写得好的技能每行都在改变行为；写得差的技能会被静默忽略，而你会以为是它没做。

## 三条原则

### 1. 修剪（Trimming）

**删掉不改变行为的内容。** 判断标准只有一个：删掉这句，AI 的行为会变吗？不会就删。

该删的典型：

- 背景介绍、设计动机、自我说明
- 重复表述（同一规则在不同小节说了三遍）
- 常识性提醒（"请注意代码质量"）
- 同一件事的举例超过一个

### 2. 指引词（Leading Words）

用一个在领域内有明确含义的词，替代一整段解释。指引词自带行为，密度远高于描述句。

| 不要说 | 说 |
|---|---|
| "把功能从上到下打通，含界面、逻辑和数据" | "纵向切片" |
| "先写会失败的测试再写实现" | "红绿重构" |
| "每次都要问，且必须给建议" | "拷问纪律" |

**方法**：一个概念需要三行以上才能讲清时，为它造词或引用既有词，然后在技能里定义一次。

本目录已用的指引词：`落盘即推送`、`活跃记忆不可变`、`纵向切片`、`红绿门禁`、`阻塞边`、`决策已锁定`。

### 3. 完成标准（Completion Criteria）

**必须写明"做完了"长什么样。** 没有完成标准，AI 会自行决定何时收尾——通常过早。

完成标准要可检验：

- ✅ "测试先失败过一次，且现在全部通过"
- ✅ "索引.json 的序号与记忆文件一一对应"
- ❌ "确保代码质量良好"
- ❌ "尽量覆盖边界情况"

## 体积纪律

- **单个 SKILL.md 不超过 100 行。** 超过后，埋在中间的条件分支会开始被静默跳过。解法是**拆成多个技能**或**删内容**，不是加小标题分节。
- frontmatter 的 `description` 是唯一常驻上下文的部分（正文只在激活时载入）。它要回答"**什么时候用我**"，不是"我是什么"。
- `triggers` 要具体。`更新`、`理解`、`记录` 这类泛词会误触发，白白消耗上下文。

## 概率性 vs 确定性

技能是概率性的，**不能用来执行无例外的硬规则**。

| 内容类型 | 该放哪 |
|---|---|
| 需要判断的流程、方法、约定 | 技能（本目录） |
| 无例外的检查（跑测试、lint、格式化） | hooks / CI / git hooks |
| 绝不外泄的凭据规则 | 环境变量 + 忽略文件 + hooks |

技能里出现"必须每次都…"时先问：这能不能交给 CI？能就交出去，技能只留**需要判断**的部分。

## 自检清单

写完技能后逐条过：

1. 删掉任意一行，行为会变吗？不变 → 删
2. 有没有能换成指引词的长解释？
3. 完成标准是可检验动作，还是模糊形容词？
4. 行数是否超过 100？
5. `description` 说的是"何时用"吗？
6. 有没有硬编码路径、命令、仓库地址？（应改为运行时发现）
7. 有没有把该放 CI 的硬规则写进来？

## 完成标准

- 七条自检全部过过一遍，并说明结论
- 行数 ≤ 100
- 无硬编码的项目相关信息
