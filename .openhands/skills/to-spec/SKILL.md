# 从共识到规格

把讨论结果写成一份**不会随会话丢失**的规格。规格是后续拆任务与验收的唯一依据。

## 铁律：规格里禁止写代码

不写代码片段、不写函数签名、不写数据库 DDL、不写伪代码。

**理由**：规格一旦掺入代码，后续修改会去照抄旧代码，而不是重新思考问题。规格定义**问题与行为**，代码是实现细节，两者生命周期不同。

允许出现的：接口的**语义契约**——输入什么、输出什么、失败时怎样，用自然语言描述。

## 规格必须包含

| 部分 | 内容 | 说明 |
|------|------|------|
| 问题 | 现在有什么痛点，为什么要做 | 不谈方案 |
| 目标行为 | 做完后系统/用户的行为变成什么样 | 用项目现有词汇 |
| 边界 | **明确列出不做什么** | 最常被省略，也最能防范围蔓延 |
| 验收 | 怎么判断做完了（可检验） | 与 tdd 的完成标准对齐 |
| 未决 | 仍需确认的事项与阻塞点 | 从 grill-me 的收尾继承 |

## 写作要求

- **用项目自己的词汇。** 不用通用术语替代已有专名；遇到新概念，先在术语表里定义再使用（见 memory 技能）。
- **只描述外部可观察的行为**，不描述内部实现结构。
- **不写"优化""提升体验"这类无法验收的形容。**
- 定稿即冻结；后续变更以**追加修订章节**方式进行，不直接改写既有结论。

## 产出位置

写到项目根目录的 `规格/<主题>.md`。任务清单由 to-tickets 写在同目录的 `<主题>_任务.md`。

项目已有既定的规格/文档目录时**沿用既有位置**，不要新建重复结构。

## 完成标准

- 五个部分齐全，边界一节非空
- 全文不含代码块（若有，移到代码里或 ticket 里）
- 每条验收标准都能被执行验证
- 用户已确认
